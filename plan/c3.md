# C3: invoice fields from rendered e-invoices

Test design, written 2026-10-09 and committed before any C3 run and before
any invoice was rendered. Shared rules: `plan/c0-common.md`. This design is
also roadmap row T8 (invoice fields, local LLM home ground); Jev has no
extraction primitive, so T8 and C3 are the same test. A change after the
commit goes into a new dated section at the end.

## Question

Can a local model read the key fields of an invoice from an image of the
page, the way an invoice arrives as a scan or PDF, and how does a vision
model compare with OCR followed by a text model?

## Why it matters for a German SME

Incoming invoices are the paperwork every company has. Since 2025 German
businesses must be able to receive e-invoices, but paper and PDF invoices
remain common for years. A local reader that gets the invoice number, the
amounts and the IBAN right is the first step of an in-house accounts
payable flow, and invoices hold bank and personal data that should stay in
house.

## Data

- Source invoices: the KoSIT XRechnung test suite,
  https://github.com/itplr-kosit/xrechnung-testsuite at commit `1ce1daf`,
  Apache-2.0, the same 34 CII files as einv1 (`plan/einv1.md`, list
  there). All 34 are used.
- Renderer: KoSIT XRechnung visualisation,
  https://github.com/itplr-kosit/xrechnung-visualization, release
  `v2026-08-31` (tag commit `e158048ec677`), Apache-2.0 (repository
  licence, read 2026-10-09). CII to the intermediate XML, then `xr-pdf.xsl`
  to XSL-FO, then PDF with Apache FOP (Apache-2.0); XSLT with Saxon-HE
  (MPL-2.0). Versions recorded. Rendering runs on a Mac, no GPU.
- Images: every PDF page rasterised at 200 dpi, PNG, greyscale, with
  `pdftoppm` (poppler, GPL-2.0, used as a tool only, nothing of it is
  shipped). The PNG has no text layer, so it stands in for a scan.
- Committed in `cases/c3/`: PDFs, PNGs (both derived from Apache-2.0 data,
  the KoSIT licence copied alongside), a manifest with SHA-256 of XML, PDF
  and every PNG.
- Limit stated in advance: every invoice has the same KoSIT layout, a clean
  table without logos or stamps. The test measures reading and field
  mapping, not robustness to layouts or bad scans.
- Exposure: the test suite XML is public on GitHub since 2017; the rendered
  pages are new, but the values could be known to a model that saw the XML.

## Fields and gold

Gold values from the CII XML by XPath, written into
`reference/c3/gold.jsonl` before any arm runs:

| field | EN 16931 | normalisation |
|---|---|---|
| invoice_number | BT-1 | trim |
| issue_date | BT-2 | ISO date |
| due_date | BT-9 | ISO date, `null` if absent |
| seller_name | BT-27 | whitespace collapsed, casefold |
| seller_vat_id | BT-31 | uppercase, no spaces, `null` if absent |
| buyer_name | BT-44 | as seller_name |
| iban | BT-84 (first) | uppercase, no spaces, `null` if absent |
| net_total | BT-109 | decimal, 2 places |
| vat_total | BT-110 | decimal, 2 places |
| gross_total | BT-112 | decimal, 2 places |
| amount_due | BT-115 | decimal, 2 places |
| currency | BT-5 | uppercase |

12 fields x 34 invoices = 408 cells. A field absent from the XML has gold
`null`; the arm must return `null` there. Before scoring, a pipeline check
(below) confirms every non-null gold value appears in the rendered PDF.

|---|---|---|---|

| `qwen3-vl-32b` | `qwen3-vl:32b` (`ff2e46876908`) | `Qwen/Qwen3-VL-32B-Instruct`, Apache-2.0, open source | 21 GB, tight: run with `num_ctx` 8192 and recorded |
| `gemma4-12b` | `gemma4:12b` (`c7597fc90b86`) | `google/gemma-4-12B-it`, Apache-2.0 (Gemma 4 licence page), open source | 7.7 GB |
| `gemma4-26b` | `gemma4:26b` (`48eb98ec778c`) | `google/gemma-4-26B-A4B-it`, Apache-2.0, open source | 16 GB |
| `mistral-small-3.2` | `mistral-small3.2:24b` (`5a408ab55df5`) | `mistralai/Mistral-Small-3.2-24B-Instruct-2506`, Apache-2.0, open source | 15 GB |

(b) OCR then a text model: docling (MIT, version recorded) converts each
PNG to Markdown with its default OCR engine, then the text model gets the
Markdown:

| arm | text model |
|---|---|
| `docling+qwen3.8-27b` | `qwen3.8:27b` (`47951e4a6661`), `Qwen/Qwen3.8-27B` Apache-2.0, open source, 18 GB |
| `docling+gemma4-12b` | `gemma4:12b` as above |

(c) Reference arm, not a scan: the PDF text layer (`pdftotext -layout`)
into `qwen3.8:27b`. It shows how much of the error is reading the image.

Dropped: Llama 3.2 Vision (its licence does not grant the multimodal
rights to companies with their principal place of business in the EU, so
it is no option for the target reader); dedicated OCR models
`deepseek-ocr` (MIT) and `glm-ocr` (MIT) return text, not fields, and are
kept as a possible later OCR arm, not in this run.

## Method

One call per invoice, all pages of the invoice as images in one message
(most invoices are one or two pages; page counts recorded). One fixed
German instruction asking for the 12 fields as JSON, with the field list
and the rule "null if the field is not on the invoice", committed verbatim
in `results/c3/method.md` before the first run. Ollama `format` set to the
JSON schema of the 12 fields (all string or null), temperature 0, seed 1.
No few-shot examples, no per-model prompt changes.

## Metrics

- Primary: field accuracy over the 408 cells, exact match after the
  normalisation above.
- Secondary: per-field accuracy (n = 34, descriptive only); invoice-level
  "all 12 right"; accuracy on the money fields together (BT-109, 110, 112,
  115) and on IBAN, since those are the fields where an error costs money.
- Bootstrap unit: invoice.
- Machine: seconds per page and per invoice (median), peak VRAM, GPU
  energy per invoice. docling time counted in its arm (OCR on GPU if docling
  uses it, recorded).

## Baseline

A regex baseline over the PDF text layer (IBAN pattern with checksum, the
first date after "Rechnungsdatum", the amount after "Gesamtbetrag",
committed before the run). It shows what a rule system gets from a
born-digital PDF without any model.

## Sanity gate

No published reference exists for field extraction on these rendered
invoices. Internal check instead, before any arm: every non-null gold value
must be found, after normalisation, in the `pdftotext` output of its PDF
(amounts in German format `1.234,56` mapped to decimal). The gate is 100 %;
a miss means the renderer drops or formats a field differently, and the
field definition is fixed in a dated section before any arm runs.

## Expected GPU time

About 3 h (34 invoices, about 60 pages, eight arms, vision prompts with
several thousand image tokens per page).

## 2026-10-09: after rendering, before any arm

Written after the 34 invoices were rendered and the render check ran, and
before any arm ran.

- Pages. The KoSIT visualisation prints every invoice on 2 to 9 pages
  (median 3, 118 pages in all), not the "about 60 pages" estimated above.
  Every page is still sent, as the method says. The money fields, parties,
  invoice number, dates and IBAN are on the first one or two pages
  ("Übersicht"); the later pages repeat details and the lines.
- Context. With up to 9 page images per call, `num_ctx` 8192 for
  `qwen3-vl-32b` would cut prompts. Every arm runs with `num_ctx` 32768.
  For `qwen3-vl-32b` (21 GB weights) this can push part of the KV cache or
  layers off the card; the runner records Ollama's `prompt_eval_count`,
  flags a call as `truncated` when it reaches the context, and the GPU log
  shows whether the model stayed on the card. Expected GPU time rises
  accordingly, to about 4 h.
- Thinking. Several candidates can think (`gemma4`, `qwen3.8`, possibly
  `qwen3-vl`). Thinking is off (`think: false`) for every model whose
  Ollama capabilities list it, as in the earlier local arms.
- Digests. The digest prefixes in the candidate table were read from the
  Ollama library pages; they do not match the manifest digests that
  `ollama list` prints (for `gemma4:12b` the PC has manifest
  `6114515d63c1`). The runner records the manifest digest and the weight
  blob digests (`/api/show`) of the tag as it is on the PC at run time; a
  tag already on the PC (`gemma4:12b`, `qwen3.8:27b`, used by T12) is not
  re-pulled.
- docling OCR engine. "Default OCR engine" is not usable as written: in
  docling 2.136.0 the automatic engine choice rejected rapidocr 3.10.0
  (version check inside docling) and ended with no engine, returning empty
  Markdown without an error (CPU probe on a Mac, 2026-10-09). The docling
  arms therefore name EasyOCR explicitly, with docling's own option
  defaults (languages en, es, fr, de; GPU when torch sees one). The runner
  stops with an error when a page comes back without text. Versions are
  recorded per run.
- Regex baseline. The layout does not print "Gesamtbetrag"; the amount to
  pay (BT-115) is labelled "Fälliger Betrag". The baseline takes the amount
  after that label, the first date after "Rechnungsdatum", and the first
  IBAN with a valid checksum; every other field is null. Result on the
  text layer: 110 of 408 cells (0.270), committed in
  `results/c3/regex-baseline/`.
- Render check: 391 of 391 non-null gold values found in the text layer
  (100 %, gate passed), `results/c3/render-check.md`. No field definition
  changed. Three invoices (03.01a, 03.04a, 03.05a) print an IBAN although
  BT-84 is absent (a direct debit account); their gold `iban` stays null,
  so an arm that copies that IBAN is wrong there.

## 2026-10-09: correction to the digest note above, before any arm

After the pulls, `ollama list` on the PC shows `qwen3-vl:8b`
`901cae732162`, `qwen3-vl:32b` `ff2e46876908` and `mistral-small3.2:24b`
`5a408ab55df5`, the prefixes in the candidate table. So the table's
prefixes are manifest digests after all, and the note above that they are
not is wrong. The two Gemma 4 tags differ from the table: `gemma4:12b` is
`6114515d63c1` (pulled for T12 on 2026-10-09, table `c7597fc90b86`) and
`gemma4:26b` is `001e5dafc3c7` (table `48eb98ec778c`); the tags were
updated on the Ollama library between reading the page and pulling. The
arms run with the tags as pulled, and the runner records the digests.

## 2026-10-10: after the run, notes on scoring and the two unfinished arms

Written after the eight arms had run in the night of 2026-10-09 to 10.
Nothing above is changed.

- Scoring: `bench/score-cap.py` rescores every cell with
  `bench/c3/fields.py` and stops if a count differs from the runner's;
  `bench/check-cap.py` rescores with its own normaliser. All agree. The
  paired test against the best arm is a bootstrap of the per-invoice
  accuracy difference over invoices; p is twice the smaller share on either
  side of 0.
- qwen3.8-27b: in both its arms it returned `null` for all four money
  fields of all 34 invoices, also from the PDF text layer. Scored as
  returned, as the method says. No prompt or schema change was tried.
- Speed: seconds per invoice is the model call plus, in the docling arms,
  the OCR of that invoice. The first three docling invoices were OCRed
  during the warm-up, so their OCR time is not in the timed pass; they are
  left out of the docling medians (31 invoices there, 34 elsewhere).
- Fits on one card: Ollama does not report the GPU/CPU split after a run,
  and the runner did not record `/api/ps`. An Ollama arm counts as
  `offloaded` when nvidia-smi memory.used reached the card (peak within
  0.5 GB of 24,564 MiB), because Ollama only fills the card when it splits
  a model. Both arms that hit this mark also show the other signs of a
  split: `qwen3-vl-32b` drew 59 W on average, and `docling+qwen3.8-27b`
  needed 19.7 s per call where the same model on the same prompt length
  took 2.1 s in the text-layer arm (EasyOCR shares the GPU in that job).
- `qwen3-vl-32b` stopped at its 180 min timeout after 17 of 34 invoices
  (median 494 s per invoice, memory full, 59 W average: model and context
  spill to the CPU). No plan-conformant cheap fix exists: `num_ctx` 8192
  would cut prompts of several page images, which is why every arm runs at
  32,768, and a lower image resolution would change the method. Recorded as
  "did not finish within the preregistered budget on one RTX 4090"; the
  per-invoice lines of its job log are kept as descriptive data
  (`results/c3/qwen3-vl-32b/2026-10-10-run1-unfinished.jsonl`), not scored.
- `qwen3-vl-8b` stopped at its 60 min timeout after 17 of 34 invoices. It
  fits (12.9 GB, 357 W average). Good calls took 28 to 59 s per invoice;
  three invoices returned empty content on both attempts after minutes of
  full GPU load, which fits a generation that runs to the end of the
  context without producing JSON. The runner keeps no raw answer of a
  failed call, so the cause is not proven. One rerun with the same code and
  settings and a 180 min queue timeout (the timeout is not part of the
  design) was enqueued on 2026-10-10 as `20261010-071202-c3-qwen3-vl-8b`,
  template `bench/queue/jobs/c3/rerun/02-qwen3-vl-8b.json`. One attempt
  only; if it also stops, the arm is recorded like the 32B one.
- Capability map: `gemma4-26b` (0.980) and `gemma4-12b` (0.978) are not
  separated (p 0.86). The roadmap rule shows the one with less peak VRAM,
  `gemma4-12b`, and the row states the tie.
