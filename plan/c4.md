# C4: structured output and tool calling

Test design, written 2026-10-09 and committed before any C4 run. Shared
rules: `plan/c0-common.md`. A change after the commit goes into a new dated
section at the end.

## Question

Do local LLMs produce output that software can consume without repair:
JSON that matches a given schema, and function calls with the right
function and the right arguments? How much does Ollama's constrained
decoding (`format` with a JSON schema) change that, and what does it cost
in speed?

## Why it matters for a German SME

An in-house model only becomes useful when it is wired into existing
software (ERP, ticketing, mail). That wiring runs through JSON and tool
calls. A model that is right in prose but breaks the format one time in
twenty needs a repair loop, which is development effort and latency.

## Data

Part A, tool calling:

- Berkeley Function Calling Leaderboard (BFCL) v3, non-live AST
  categories, from the repository https://github.com/ShishirPatil/gorilla
  at commit `6ea57973c7a6` (Apache-2.0, repository licence, read
  2026-10-09), folder `berkeley-function-call-leaderboard`, files for
  `simple` (Python, 400), `multiple` (200), `parallel` (200),
  `parallel_multiple` (200) with their `possible_answer` files. All 1,000
  items, no sampling. The Hugging Face mirror
  `gorilla-llm/Berkeley-Function-Calling-Leaderboard` (Apache-2.0, revision
  `61fc0608cfd8`) is used only if the repository files are unavailable.
- Scoring with the official AST checker of the `bfcl-eval` package (same
  commit), not a reimplementation.
- English prompts. The task is about format discipline; a German variant is
  not part of this run.

Part B, JSON schema adherence:

- JSONSchemaBench, `epfl-dlab/JSONSchemaBench`, revision
  `5bd0f4640bad`, licence MIT (card, read 2026-10-09), split `test`.
- Sample: 100 schemas from each of the six subsets `Github_easy`,
  `Github_medium`, `Github_hard`, `Glaiveai2K`, `Kubernetes`,
  `JsonSchemaStore` (600 schemas), drawn per subset by sorting on the row
  index and taking the first 100 of a permutation from numpy
  `default_rng(20261009)`, one generator per subset in that order. A subset
  with fewer than 100 test rows keeps all.

Exposure: BFCL is public since 2024 and widely used in tool-calling
fine-tuning; JSONSchemaBench since 2025. Both are likely in the training
data of recent models.

## Method

Part A, two modes per model: `fc` (Ollama native `tools` field, the model's
own chat template) and `prompt` (functions as JSON in the system prompt,
answer parsed from text, BFCL's prompt-mode format). Part B, two modes:
`free` (schema in the prompt, plain generation, first JSON object parsed)
and `constrained` (same prompt plus Ollama `format` = the schema). A schema
Ollama rejects for `format` counts as "not constrainable" and is reported
as a coverage number, scored in `free` mode only.

## Metrics

- Part A primary: AST accuracy over the 1,000 items (BFCL checker),
  per mode. Secondary: accuracy per category; share of unparseable
  answers.
- Part B primary: share of the 600 outputs that parse and validate against
  their schema (`jsonschema`, MIT, Draft 2020-12 or the schema's declared
  draft), per mode. Secondary: coverage of `constrained` mode; validity per
  subset. Validity says nothing about whether the content is sensible;
  that is not scored.
- Bootstrap unit: item (A), schema (B); McNemar between modes of the same
  model.
- Machine: median ms per item, output tokens per second, the slowdown of
  `constrained` over `free`, peak VRAM, GPU energy per 1,000 items.

## Baseline

Part A: the BFCL leaderboard numbers of the same model families (below),
as an outside anchor rather than a trivial baseline. Part B: `free` mode is
the baseline for `constrained`.

## Sanity gate

Reference: BFCL leaderboard non-live table
(https://gorilla.cs.berkeley.edu/data_non_live.csv, read 2026-10-09):
Qwen3-14B (FC) Python Simple AST 95.25 %, Multiple AST 93.00 %. `qwen3-14b`
in `fc` mode runs first; both numbers must lie within 5 points (the
leaderboard ran full precision, we run Q4_K_M through Ollama). Outside
that, the template and the parser are checked before anything else runs.

## Expected GPU time

About 3 h (8 models x 2 modes x 1,000 items, plus 8 x 2 x 600 schemas).
