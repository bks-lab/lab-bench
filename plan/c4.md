# C4: structured output and tool calling

Test design, written 2026-10-09 and committed before any C4 run. Shared
rules: `plan/c0-common.md`. A change after the commit goes into a new dated
section at the end.

## Question

Do local LLMs produce output that software can consume without repair:
JSON that matches a given schema, and function calls with the right
function and the right arguments? How much does Ollama's constrained
decoding (`format` with a JSON schema) change that, and what does it cost
in speed?

## Why it matters for a German SME

An in-house model only becomes useful when it is wired into existing
software (ERP, ticketing, mail). That wiring runs through JSON and tool
calls. A model that is right in prose but breaks the format one time in
twenty needs a repair loop, which is development effort and latency.

## Data

Part A, tool calling:

- Berkeley Function Calling Leaderboard (BFCL) v3, non-live AST
  categories, from the repository https://github.com/ShishirPatil/gorilla
  at commit `6ea57973c7a6` (Apache-2.0, repository licence, read
  2026-10-09), folder `berkeley-function-call-leaderboard`, files for
  `simple` (Python, 400), `multiple` (200), `parallel` (200),
  `parallel_multiple` (200) with their `possible_answer` files. All 1,000
  items, no sampling. The Hugging Face mirror
  `gorilla-llm/Berkeley-Function-Calling-Leaderboard` (Apache-2.0, revision
  `61fc0608cfd8`) is used only if the repository files are unavailable.
- Scoring with the official AST checker of the `bfcl-eval` package (same
  commit), not a reimplementation.
- English prompts. The task is about format discipline; a German variant is
  not part of this run.

Part B, JSON schema adherence:

- JSONSchemaBench, `epfl-dlab/JSONSchemaBench`, revision
  `5bd0f4640bad`, licence MIT (card, read 2026-10-09), split `test`.
- Sample: 100 schemas from each of the six subsets `Github_easy`,
  `Github_medium`, `Github_hard`, `Glaiveai2K`, `Kubernetes`,
  `JsonSchemaStore` (600 schemas), drawn per subset by sorting on the row
  index and taking the first 100 of a permutation from numpy
  `default_rng(20261009)`, one generator per subset in that order. A subset
  with fewer than 100 test rows keeps all.

Exposure: BFCL is public since 2024 and widely used in tool-calling
fine-tuning; JSONSchemaBench since 2025. Both are likely in the training
data of recent models.

## Method

Part A, two modes per model: `fc` (Ollama native `tools` field, the model's
own chat template) and `prompt` (functions as JSON in the system prompt,
answer parsed from text, BFCL's prompt-mode format). Part B, two modes:
`free` (schema in the prompt, plain generation, first JSON object parsed)
and `constrained` (same prompt plus Ollama `format` = the schema). A schema
Ollama rejects for `format` counts as "not constrainable" and is reported
as a coverage number, scored in `free` mode only.

## Metrics

- Part A primary: AST accuracy over the 1,000 items (BFCL checker),
  per mode. Secondary: accuracy per category; share of unparseable
  answers.
- Part B primary: share of the 600 outputs that parse and validate against
  their schema (`jsonschema`, MIT, Draft 2020-12 or the schema's declared
  draft), per mode. Secondary: coverage of `constrained` mode; validity per
  subset. Validity says nothing about whether the content is sensible;
  that is not scored.
- Bootstrap unit: item (A), schema (B); McNemar between modes of the same
  model.
- Machine: median ms per item, output tokens per second, the slowdown of
  `constrained` over `free`, peak VRAM, GPU energy per 1,000 items.

## Baseline

Part A: the BFCL leaderboard numbers of the same model families (below),
as an outside anchor rather than a trivial baseline. Part B: `free` mode is
the baseline for `constrained`.

## Sanity gate

Reference: BFCL leaderboard non-live table
(https://gorilla.cs.berkeley.edu/data_non_live.csv, read 2026-10-09):
Qwen3-14B (FC) Python Simple AST 95.25 %, Multiple AST 93.00 %. `qwen3-14b`
in `fc` mode runs first; both numbers must lie within 5 points (the
leaderboard ran full precision, we run Q4_K_M through Ollama). Outside
that, the template and the parser are checked before anything else runs.

## Expected GPU time

About 3 h (8 models x 2 modes x 1,000 items, plus 8 x 2 x 600 schemas).

## 2026-10-10: preparation notes (before any C4 run)

Written after the inputs were frozen and before any C4 arm ran. Nothing
above is changed; these notes say how the design is applied where it left
room, and where it could not be followed as written.

- Files. At the pinned commit `6ea57973c7a6` the data files carry the
  prefix `BFCL_v4_` (`BFCL_v4_simple_python.json`, `BFCL_v4_multiple.json`,
  `BFCL_v4_parallel.json`, `BFCL_v4_parallel_multiple.json` and their
  `possible_answer` files). The four non-live AST categories are the v3
  sets with the counts of the design (400, 200, 200, 200). Hashes in
  `cases/c4/manifest.json`, the requests of both modes in
  `cases/c4/bfcl.jsonl` (`bench/c4/build_c4.py`).
- Checker. `bfcl-eval` is not installed as a package (it pins numpy 1.26
  and pulls about thirty API clients). `bench/c4/bfcl_shim.py` imports the
  checkout as it is and replaces only the model table
  (`constants/model_config.py`), whose one flag the checker reads is
  `underscore_to_dot`. Dataset loader, function doc processing, tool
  conversion, prompt-mode system prompt, decoder and `ast_checker` are the
  upstream code, called through BFCL's own `_evaluate_single_ast_entry`
  (`bench/c4/check_ast.py`).
- Modes in detail, fixed in `results/c4/method.md`: `fc` converts the
  functions as BFCL's OpenAI completions handler does (a dot in a name
  becomes `_`, the checker maps it back), which is how the leaderboard ran
  the reference row "Qwen3-14B (FC)". That row ran with thinking on
  (`enable_thinking: true` in BFCL's Qwen handler); this run has thinking
  off as designed, so the gate compares a non-thinking run with a thinking
  one. The tolerance stays 5 points.
- Thinking is switched off with Ollama's `think: false` rather than a
  `/no_think` text, the API switch for the same template mechanism, for
  every model whose Ollama capabilities list thinking. gpt-oss gets
  `think: "low"`.
- Generation caps, not in the design: `num_predict` 1024 in Part A and
  4096 in Part B, so a model that does not stop cannot hold the queue. A
  capped answer is scored as returned.
- Part B prompt: one user message, the instruction in `results/c4/method.md`
  with the schema re-serialised without indentation (same content), to keep
  long schemas inside `num_ctx` 8192 as far as possible. 72 of the 600
  schemas are longer than 24,000 characters as committed; a prompt that
  reaches the context is flagged (`truncated_prompt`) and scored as
  returned. Parsing and validation rules as in `results/c4/method.md`;
  format checking is off. All 600 sampled schemas are valid for their
  declared draft (checked 2026-10-10).
- Sampling: "one generator per subset" is read as a fresh
  `default_rng(20261009)` for each subset. Every subset has at least 100
  test rows, so 600 schemas.
- Tags. `granite4:3b` is pulled as `granite4:micro`: the PC has that tag
  with manifest digest `89962fcc7523`, the digest the candidate table gives
  for `granite4:3b`, so the weights are the same. `qwen3:8b` was pulled on
  2026-10-10 with digest `500a1f067a9f` (as in the table). `gpt-oss:20b`
  was pulled the same day with digest `f38aa0c53da5`, not the table's
  `17052f91a42e`: the library tag changed in between. `qwen3.8:27b` is
  `aaee06c39dcf` (pulled for T12) and the Gemma 4 tags are as in the
  correction of `plan/c3.md`. The runner records every digest.
- Sanity gate procedure: the AST checker runs on the Mac, not in the PC
  job. The `qwen3-14b` job runs alone first; its rows are checked on the
  Mac, and the other seven arms are enqueued only when `simple_python`
  and `multiple` in `fc` mode lie within 5 points of 95.25 % and 93.00 %.
- Capability map: the row shows the arm with the highest AST accuracy in
  `fc` mode (native tool calling, the path software integration uses),
  with the roadmap's tie rule, and gives the `constrained` schema validity
  of the same arm next to it. Energy per 1,000 items comes from the timed
  section of each mode.

## 2026-10-10: run time of the first arm (before the other arms)

Written after the sanity arm ran and before any other C4 arm. Nothing above
is changed.

- Gate: `qwen3-14b` in `fc` mode reached 93.50 % on `simple_python`
  (leaderboard 95.25) and 94.00 % on `multiple` (leaderboard 93.00), both
  within 5 points. Passed; the other seven arms were enqueued.
- Time: the arm needed 108 GPU minutes, not the 20 or so the design's 3 h
  for eight models implied. Part B dominates: 1,200 generated JSON objects
  with a median of about 1.4 s and a long tail (long schemas, answers up to
  the 4,096 token cap). The queue timeouts of the remaining arms were raised
  to 2.5 times a per-arm estimate before they started
  (`bench/queue/jobs/c4/`); the design is unchanged.
