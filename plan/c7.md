# C7: long context on one card

Test design, written 2026-10-09 and committed before any C7 run. Shared
rules: `plan/c0-common.md`. A change after the commit goes into a new dated
section at the end.

## Question

Up to which input length does a local model on 24 GB still find what is in
its context, and what does the length cost in VRAM and time to first
token?

## Why it matters for a German SME

Contracts, tenders and minutes are long. A model card may claim 128k
tokens, but on one card the key-value cache competes with the weights for
memory, and retrieval inside the context can degrade long before the
claimed limit. The answer decides whether a whole document can be given to
the model or must be cut and searched (C1).

## Data

Synthetic, generated by `bench/gen-c7.py`, committed with the design's
first implementation and before any run:

- Haystack: German filler text made from the GermanQuAD test passages (CC
  BY 4.0, as in C6), concatenated in a seeded order (`default_rng(20261009)`)
  until the target length.
- Target lengths: 4k, 16k and 32k tokens, measured with each model's own
  tokenizer via Ollama `prompt_eval_count` on a dry call; the generator
  trims to within 2 % of the target and records the real count.
- Tasks (in the style of RULER, own code):
  - `single`: one needle "Der Freigabecode für Projekt <Name> lautet
    <7 digits>." and the question for that code.
  - `multikey`: four needles with four different project names, question
    for one of them.
  - `multivalue`: one project with three codes in three places, question
    for all three.
- Needle depth 10 %, 50 % and 90 % of the haystack (for `multikey` and
  `multivalue` the depth of the asked needle; the others are placed with
  the seeded generator).
- 20 trials per cell with fresh names and codes: 3 lengths x 3 tasks x 3
  depths x 20 = 540 prompts per model. Names come from a fixed list of
  invented project names; codes from the generator.
- Exposure: none, the needles are generated per run.

## Candidates

Ollama, `num_ctx` set to the target length plus 512, temperature 0, seed 1,
flash attention as Ollama's default for the GPU (recorded), KV cache type
`f16` (and, as a second pass only for a model that does not fit at 32k,
`q8_0`, labelled so):

| arm | tag | licence, class | weights |
|---|---|---|---|
| `qwen3-8b` | `qwen3:8b` | Apache-2.0, open source | 5.2 GB |
| `qwen3-14b` | `qwen3:14b` | Apache-2.0, open source | 9.3 GB |
| `gemma4-12b` | `gemma4:12b` | Apache-2.0, open source | 7.7 GB |
| `gemma4-26b` | `gemma4:26b` | Apache-2.0, open source | 16 GB |
| `mistral-small-3.2` | `mistral-small3.2:24b` | Apache-2.0, open source | 15 GB |
| `qwen3.8-27b` | `qwen3.8:27b` | Apache-2.0, open source | 18 GB |
| `gpt-oss-20b` | `gpt-oss:20b` | Apache-2.0, open source | 14 GB |

A model whose weights plus cache at a length do not fit in VRAM (Ollama
offloads layers to the CPU, visible in `ollama ps`) is run anyway and
marked `offloaded`, because that is what a user would get; its speed is
reported separately and it is not eligible as "fits on one card" at that
length.

## Metrics

- Primary: accuracy per model and length, pooled over tasks and depths
  (n = 180 per length). An answer is right if every asked code appears in
  the answer as a 7-digit string and no wrong code from the haystack does.
- Secondary: accuracy per task and per depth (descriptive); the longest
  length with accuracy at or above 90 % per model.
- Bootstrap unit: prompt.
- Machine: peak VRAM per length, time to first token (prompt processing)
  per length, `offloaded` flag, GPU energy per prompt per length.

## Baseline

Chance is effectively zero (a 7-digit code). The 4k result of each model
is its own baseline for the decline.

## Sanity gate

No published reference applies to this generator. Internal check: every
model must reach at least 95 % on `single` at 4k (60 prompts). A model
below that is checked for prompt or template faults before its long runs.

## Expected GPU time

About 4 h (7 models x 540 prompts; the 32k prompts dominate).

## 2026-10-10: preparation notes (before any C7 run)

Written after `bench/gen-c7.py` and `cases/c7/` were committed and before
any C7 arm ran. Nothing above is changed.

- Generator: the model-independent part of all 540 prompts (names, codes,
  needle depths, the seeded passage order of each trial) is frozen in
  `cases/c7/trials.jsonl`. Haystack passages are the 474 distinct test
  contexts in id order; none contains a run of exactly seven digits. A
  needle is the sentence "Der Freigabecode für Projekt <Name> lautet
  <Code>." inserted at the sentence boundary nearest its depth (share of
  the haystack's characters). In `multikey` the three other needles get
  depths from the generator (uniform 0.02 to 0.98); in `multivalue` the
  first of the three codes is at the cell's depth, the other two at
  generated depths. Prompt, needle and questions are in the manifest.
- Length: the runner measures per model and length how many haystack
  characters give the target prompt length in the model's own tokens
  (Ollama `prompt_eval_count`, one call with an empty haystack, then dry
  calls until two measurements agree), aiming at 99 % of the target so
  that a prompt stays inside `num_ctx` (target plus 512). Every call
  records its real prompt length. A trial whose text tokenizes differently
  and lands outside 98 to 102 % of the target is rescaled and sent again,
  at most twice (a probe on 2026-10-10 put 4 of 9 prompts at 4k outside the
  band, none at 32k); the discarded attempts are kept in the row, and a
  prompt still outside is flagged `length_off` and scored. The trimming
  therefore happens per model in the runner, not in the generator.
- Right answer: every asked code appears as a seven-digit string and no
  code of another needle of the same prompt does.
- Calls: `/api/chat`, `temperature` 0, `seed` 1, `num_predict` 512, thinking
  off (`think: false`), gpt-oss `think: "low"`. Time to first token is
  Ollama's prompt evaluation time of the call.
- Sanity gate: the 60 `single` prompts at 4k run first in each job; below
  95 % the job stops with exit 3 before any long prompt.
- KV cache: the `f16` pass uses the workstation's Ollama service as it runs
  (its defaults: f16 cache, flash attention as Ollama decides). The
  `q8_0` pass starts a private `ollama serve` on another port with
  `OLLAMA_KV_CACHE_TYPE=q8_0` and flash attention on (q8_0 requires it) and
  runs only the lengths at which the f16 pass was offloaded.
- Offloaded: read from Ollama `/api/ps` (`size_vram` below `size`) during
  each length, and recorded.
- Capability map: the row shows the arm with the highest pooled accuracy at
  32k among the f16 passes, with the roadmap's tie rule; "fits on one 24 GB
  card" is that arm's offload state at 32k.
- `qwen3:8b` and `gpt-oss:20b` were pulled on 2026-10-10 (digests in
  `plan/c4.md`, preparation notes).
