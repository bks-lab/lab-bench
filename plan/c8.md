# C8: throughput and energy per model size

Test design, written 2026-10-09 and committed before any C8 run. Shared
rules: `plan/c0-common.md`. A change after the commit goes into a new dated
section at the end.

## Question

How many tokens per second, and how many short decisions per hour, does
one RTX 4090 deliver per model size, with one user and with several
parallel requests, and what does that cost in watts?

## Why it matters for a German SME

Sizing is the first question of every in-house plan: how many colleagues
can one card serve, and what does it cost in electricity. Quality tests
(C1 to C7, C9) give one latency per model; C8 gives the load curve.

## Workloads

Synthetic and fixed, generated by `bench/gen-c8.py` (committed before the
run, seed 20261009):

- `chat-short`: prompt of 512 tokens (German business text from the C6
  passages), generation capped at 256 tokens (`num_predict` 256) with an
  instruction to write a long summary, so most calls reach the cap; actual
  tokens recorded.
- `chat-long`: prompt of 4,096 tokens, generation 256.
- `decide`: 500 route1 MASSIVE de scenario questions
  (`requests/route1/requests.jsonl`, first 500 of a seeded permutation),
  answered with the bench's existing one-token method
  (`bench/run-local.mjs`), which is the "decision" of the map.

Concurrency levels 1, 4, 8 and 16 parallel clients; Ollama restarted with
`OLLAMA_NUM_PARALLEL` equal to the level and `OLLAMA_MAX_LOADED_MODELS=1`.
Each level runs 64 requests for the chat workloads (after 4 warm-up) and
all 500 for `decide`. Each configuration is repeated three times.

## Metrics

- Prompt processing tokens per second and generation tokens per second
  (Ollama `prompt_eval_count / prompt_eval_duration`, `eval_count /
  eval_duration`), per request and aggregated over all streams.
- Time to first token, p50 and p95.
- `decide`: decisions per hour at each concurrency, from wall time.
- Energy: GPU joules per 1,000 generated tokens and per 1,000 decisions,
  mean and peak power, from the 1 s nvidia-smi samples.
- Peak VRAM per concurrency level.
- Uncertainty: medians with bootstrap intervals over requests; aggregate
  throughput as mean and range of the three repetitions.

## Baseline

Concurrency 1 of the same model is the baseline for the scaling factor
(aggregate tokens per second at n / at 1).

## Sanity gate

No published reference fits this exact setup (Ollama version, quantisation,
power limit). Internal check: the three repetitions of `chat-short` at
concurrency 1 must agree within 5 % (coefficient of variation) per model,
and the GPU must be idle (no other compute process in `nvidia-smi`) before
every configuration. A failure stops the run until the cause (thermal
throttling, another process, power limit) is found and recorded.

## Expected GPU time

About 3 h for Ollama (9 models x 4 levels x 3 workloads x 3 repetitions,
mostly short), plus about 1 h if the vLLM arm runs.

## 2026-10-10: preparation notes (before any C8 run)

Written after `bench/gen-c8.py` and `cases/c8/` were committed and before
any C8 arm ran. Nothing above is changed.

- Ollama per concurrency level: the design restarts "Ollama" with
  `OLLAMA_NUM_PARALLEL` set. The workstation's Ollama service is not
  restarted (it serves other uses, and the queue runner does not restart
  it). Instead each level starts a private `ollama serve` on its own port
  with `OLLAMA_NUM_PARALLEL` = the level and `OLLAMA_MAX_LOADED_MODELS=1`,
  reading the same model folder; the queue gate guarantees the service
  holds no model when the job starts. Same binary (0.35.0), same weights.
- Prompts: `chat-short` and `chat-long` each have 4 warm-up and 64 timed
  prompts, every prompt with its own passage order, so no two prompts
  share text after the instruction (no prompt cache reuse). The runner
  measures per model how many characters of passage text make 512 and
  4,096 prompt tokens with the model's template and tokenizer and cuts
  there; the real counts are recorded. The instruction asks for at least
  600 words, `num_predict` 256.
- `num_ctx` 4608 for every workload (4,096 prompt plus 256 generated plus
  the template, per parallel slot). The one-token method of
  `bench/run-local.mjs` uses 16,384; a larger context only reserves more
  cache memory, the one-token answer does not depend on it, and 16,384 per
  slot at 16 slots would not fit the card.
- `decide`: the first 500 of the seeded permutation of the 2,974 MASSIVE de
  lines, their `scenario` question, rendered by `bench/c8/decide-prompts.mjs`
  exactly as `run-local.mjs` does (route system line, prefix `''`, top 20
  logprobs, one token). gpt-oss has no template in the bench and no switch
  to turn reasoning off; for this timed-only workload its assistant turn is
  opened directly in the final channel (`harmony` in the manifest).
- Order per arm: level 1, 4, 8, 16; per level the three workloads; per
  workload three repetitions, each after its own warm-up. Chat requests
  stream, so time to first token is measured by the client (at a level
  above 1 it includes waiting for a free slot, and is labelled so).
- Gate: the coefficient of variation uses the sample standard deviation of
  the three aggregate generation rates. The idle check before every
  configuration reads GPU utilisation three times while our model is
  loaded and idle, and the service's `/api/ps`; foreign load that does not
  clear within 10 minutes ends the job with exit 4.
- Capability map: C8 has no quality metric, so its row names no "best"
  model by quality. It carries one line per arm (aggregate generation
  tokens per second at concurrency 1 and 16 for `chat-short`, decisions per
  hour at 16, GPU joules per 1,000 generated tokens at 16, peak VRAM,
  offloaded or not), and its headline cell is the arm with the most
  decisions per hour at concurrency 16 among the arms that stay on the card.
- Arms: `granite4-3b` runs as `granite4:micro` (same digest, see
  `plan/c4.md`), `qwen3:8b` and `gpt-oss:20b` were pulled on 2026-10-10.

## 2026-10-10, later: changes after the dry runs (before any C8 run)

Written after short dry runs through the queue (not scored) and before any
C8 arm ran. Nothing above is changed.

- Prompt cache. The `llama-server` that Ollama 0.35.0 starts keeps up to
  8 GiB of earlier prompts in host memory and restores them. In a dry run
  the second and third repetition of `chat-long` were 19 % faster than the
  first, because they skipped prompt processing the first had done. The
  private server now starts with `LLAMA_ARG_CACHE_RAM=0`, which the runner
  passes to `llama-server` (its log then says "prompt cache is disabled");
  the three repetitions of the next dry run agreed to 0.4 %. The cache of
  each slot (its last prompt) stays, as in normal use. For the same reason
  the vLLM arm runs with `--no-enable-prefix-caching`.
- Context: `num_ctx` (vLLM `--max-model-len`) is 5120, not 4608. The
  calibration hits 4,096 tokens on average, but single `chat-long` prompts
  reach about 4,400 tokens with Gemma's tokenizer, and vLLM refused two of
  them with 4608 (prompt plus 256 to generate did not fit).
- vLLM arm: WSL2 Ubuntu 24.04 with the GPU visible was present, so the arm
  runs as designed. vLLM 0.31.0 (torch 2.13.0, CUDA 13.0) installed into a
  user-level venv without system changes; three settings were needed to
  start it on this machine: a uv-managed CPython (the system Python has no
  headers for triton's launcher), a Linux-only `PATH` (the Windows `PATH`
  that WSL appends holds an `nvcc` torch cannot run), and vLLM's PyTorch
  sampler instead of FlashInfer's (`VLLM_USE_FLASHINFER_SAMPLER=0`;
  FlashInfer compiles its kernel with `nvcc`, which the WSL Ubuntu does not
  have). Weights: `Qwen/Qwen3-14B-AWQ` at `31c69efc2946` (Qwen's own AWQ
  INT4 build) and `cyankiwi/gemma-4-12B-it-AWQ-INT4` at `ad2d7e521f3e`
  (a community AWQ INT4 build of `google/gemma-4-12B-it`, Apache-2.0; no
  4-bit build by Google exists). Thinking off through the chat template's
  `enable_thinking`. vLLM reports no per-request durations: generation time
  per request is the client's time from the first to the last streamed
  token.
