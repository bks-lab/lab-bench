# C8: throughput and energy per model size

Test design, written 2026-10-09 and committed before any C8 run. Shared
rules: `plan/c0-common.md`. A change after the commit goes into a new dated
section at the end.

## Question

How many tokens per second, and how many short decisions per hour, does
one RTX 4090 deliver per model size, with one user and with several
parallel requests, and what does that cost in watts?

## Why it matters for a German SME

Sizing is the first question of every in-house plan: how many colleagues
can one card serve, and what does it cost in electricity. Quality tests
(C1 to C7, C9) give one latency per model; C8 gives the load curve.

## Workloads

Synthetic and fixed, generated by `bench/gen-c8.py` (committed before the
run, seed 20261009):

- `chat-short`: prompt of 512 tokens (German business text from the C6
  passages), generation capped at 256 tokens (`num_predict` 256) with an
  instruction to write a long summary, so most calls reach the cap; actual
  tokens recorded.
- `chat-long`: prompt of 4,096 tokens, generation 256.
- `decide`: 500 route1 MASSIVE de scenario questions
  (`requests/route1/requests.jsonl`, first 500 of a seeded permutation),
  answered with the bench's existing one-token method
  (`bench/run-local.mjs`), which is the "decision" of the map.

Concurrency levels 1, 4, 8 and 16 parallel clients; Ollama restarted with
`OLLAMA_NUM_PARALLEL` equal to the level and `OLLAMA_MAX_LOADED_MODELS=1`.
Each level runs 64 requests for the chat workloads (after 4 warm-up) and
all 500 for `decide`. Each configuration is repeated three times.

vLLM: it has no native Windows build. If a WSL2 Ubuntu with CUDA is
present on the PC when C8 starts, a second engine arm runs `gemma4-12b` and

quantisation (AWQ or FP8, named per row), at the same concurrency levels.

"engine plus quantisation", never as engine alone. If WSL2 is not set up,
the vLLM arm is `not_run` with that reason; setting it up is not part of
this test.

## Metrics

- Prompt processing tokens per second and generation tokens per second
  (Ollama `prompt_eval_count / prompt_eval_duration`, `eval_count /
  eval_duration`), per request and aggregated over all streams.
- Time to first token, p50 and p95.
- `decide`: decisions per hour at each concurrency, from wall time.
- Energy: GPU joules per 1,000 generated tokens and per 1,000 decisions,
  mean and peak power, from the 1 s nvidia-smi samples.
- Peak VRAM per concurrency level.
- Uncertainty: medians with bootstrap intervals over requests; aggregate
  throughput as mean and range of the three repetitions.

## Baseline

Concurrency 1 of the same model is the baseline for the scaling factor
(aggregate tokens per second at n / at 1).

## Sanity gate

No published reference fits this exact setup (Ollama version, quantisation,
power limit). Internal check: the three repetitions of `chat-short` at
concurrency 1 must agree within 5 % (coefficient of variation) per model,
and the GPU must be idle (no other compute process in `nvidia-smi`) before
every configuration. A failure stops the run until the cause (thermal
throttling, another process, power limit) is found and recorded.

## Expected GPU time

About 3 h for Ollama (9 models x 4 levels x 3 workloads x 3 repetitions,
mostly short), plus about 1 h if the vLLM arm runs.
