# C9: personal data detection in German text (DSGVO)

Test design, written 2026-10-09 and committed before any C9 run. Shared
rules: `plan/c0-common.md`. This design is also roadmap row T7 (personal
data detection, home ground of GLiNER extraction and PII); Jev has no span
primitive, so T7 and C9 are the same test. A change after the commit goes
into a new dated section at the end.

## Question

How reliably do local tools find personal data in German business
documents: a span model (GLiNER PII), a rule and NER system (Microsoft
Presidio) and a local LLM? Which one misses least, and how fast is it?

## Why it matters for a German SME

Under the DSGVO, a company that wants to send text to any model, or keep
it in a search index, first needs to find and mask the personal data in
it. A local detector is the precondition for many other uses, and its
recall (what it misses) matters more than its precision.

## Data

- Primary: `gretelai/synthetic_pii_finance_multilingual`, revision
  `7b844d167385`, licence Apache-2.0 (card, read 2026-10-09), split
  `test`, rows with `language == "German"`: 476 documents (counted by the
  Hugging Face dataset statistics on 2026-10-09; the runner records its
  own count). Spans in `pii_spans` (character offsets, label). All 476 are
  used.
- The texts are synthetic, generated by an LLM in a finance domain
  (statements, loan applications, SWIFT and EDI messages), and so are the
  span labels. That makes the gold itself a model output. Gold audit,
  before any arm runs: one BKS-Lab person checks a seeded sample of 40
  documents (`default_rng(20261009)` over the sorted ids) for missed and
  wrong spans, blind to every arm. If the audited gold precision or recall
  is below 0.90, the test is reported as "gold noisy", all numbers are
  descriptive only, and no ranking claim is made.
- Label mapping: Gretel's label inventory is read from the `train` split
  only and mapped, before the run, to seven types written into
  `reference/c9/labels.json`: `person`, `address`, `email`, `phone`,
  `iban_account` (IBAN, account and card numbers), `id_number` (tax, social
  security, customer, passport and similar ids), `date_of_birth`. Labels
  that are not personal data in the DSGVO sense (company names, generic
  dates, amounts) are dropped from gold and predictions alike, and the
  mapping table is committed.
- Committed: `cases/c9/` with the 476 German rows (Apache-2.0, licence
  copied).
- Exposure: public since 2024; may be in training data of the LLM arms and
  of GLiNER PII models.

Not used: `ai4privacy/pii-masking-400k` and `-300k` (custom licence file,
not an open licence); `ai4privacy/open-pii-masking-500k-ai4privacy` (its
card metadata says CC BY 4.0, but its licence section puts the Llama
Community Licence and acceptable use policy on the data, which does not
fit the bench's CC BY 4.0 data licence). A real, human-annotated German PII
set with an open licence was not found.

## Candidates

| arm | model | revision | licence, class |
|---|---|---|---|
| `gliner-multi-pii` | `urchade/gliner_multi_pii-v1` | `1fcf13e85f4e` | Apache-2.0, open source |
| `gliner-pii-domains` | `E3-JSI/gliner-multi-pii-domains-v1` | `66b7951b1e02` | Apache-2.0, open source |
| `gliner2.5-multi` | `fastino/gliner2.5-multi-v1` (the bench's ex1 arm) | `cf5593a5d45e` | Apache-2.0, open source |
| `presidio` | Microsoft Presidio analyzer (MIT, version recorded) with spaCy `de_core_news_lg` (MIT) and its built-in pattern recognisers, language `de` | recorded | MIT, open source |
| `qwen3.8-27b` | `qwen3.8:27b`, JSON list of `{text, type}`, offsets by exact string search | digest | Apache-2.0, open source |
| `gemma4-12b` | `gemma4:12b`, same prompt | digest | Apache-2.0, open source |

GLiNER arms get the seven type names in German and English as labels
(fixed list in `reference/c9/labels.json`), threshold 0.5, no tuning, text
chunked at 384 words with 50 words overlap. LLM arms: one fixed German
instruction listing the seven types, temperature 0, seed 1, Ollama
`format` JSON schema. An LLM span whose text is not found in the document
counts as a false positive.

Dropped: `nvidia/gliner-PII` (English, NVIDIA Open Model Licence),
`knowledgator/gliner-pii-base-v1.0` (English only per its card).

## Metrics

- Primary: type-agnostic span F1, exact boundaries after trimming
  whitespace and trailing punctuation. Recall is reported next to it and
  is the number the capability map shows as "misses".
- Secondary: typed strict F1 per type (descriptive), character-level
  masking recall (share of gold PII characters covered by any predicted
  span), and the same numbers on the 40 audited documents with the audited
  gold.
- Bootstrap unit: document; paired bootstrap between arms.
- Machine: ms per document and characters per second, peak VRAM, GPU
  energy per 1,000 documents. Presidio runs on CPU and says so.

## Baseline

Regex only: e-mail, IBAN (with checksum), German phone number patterns,
committed before the run.

## Sanity gate

No published reference exists for any candidate on this German subset.
Internal check instead: the regex baseline must reach recall of at least
0.95 on the gold `email` spans. That tests the offset handling, the label
mapping and the scorer on the easiest type; a miss there is a pipeline
fault, not a model result.

## Expected GPU time

About 1.5 h (476 documents; GLiNER arms are fast, the two LLM arms take
most of it).

## 2026-10-12: preparation notes (before any C9 model arm)

Written after the inputs were frozen and the sanity arm had run on the Mac,
before any model arm ran. Nothing above is changed.

- Inputs: `bench/c9/freeze.py` reads `data/test-00000-of-00001.parquet` at
  revision `7b844d167385` (SHA-256 in the script) and keeps the 476 rows
  with `language == "German"`, sorted on Gretel's integer `index` (the id).
  `docs.jsonl` holds text and raw gold spans unchanged,
  `cases/c9/manifest.json` hashes, ids, the 40 audit ids and the label
  counts of the `train` split (29 labels; the German test rows use no label
  outside them). The `German_test` file of the repository has 453 rows and
  is not used; the design names the `test` split.
- Deviation from "Committed: `cases/c9/`": GitHub's push protection
  rejected `docs.jsonl` because two invented documents carry API keys in
  real provider formats (a Slack bot token, AWS key ids; Gretel's generator
  made them up, they are labelled `api_key` in the gold). The documents are
  not changed to get past it. Until a maintainer clears the keys as test
  data on GitHub, `docs.jsonl` stays out of git: `freeze.py` rebuilds it
  byte for byte into `.cache/c9/` (its SHA-256 is in the committed
  manifest), and the workstation reads it from `D:\bench-data\c9`.
- Label mapping (`reference/c9/labels.json`, reasons per label): name,
  first and last name to `person`; street address and coordinates to
  `address`; IBAN, BBAN and card number to `iban_account`; SSN, customer,
  employee, passport and driving licence numbers, user name and IP addresses
  (online identifiers under Art. 4(1) DSGVO) to `id_number`. Dropped:
  company, date, time, timestamp, SWIFT/BIC and routing number (identify a
  bank), and the secrets API key, password, PIN and card security code
  (secrets, not identifiers of a person). After mapping and the boundary
  rule, duplicates removed: 1,754 gold spans (person 1,089, address 356,
  id_number 106, email 86, phone 49,
  iban_account 43, date_of_birth 25).
- Sanity gate, run on the Mac before any model arm
  (`bench/c9/run_c9.py --arm regex --gate 0.95`): with the boundary rule of
  the design (whitespace and trailing punctuation trimmed) the regex
  baseline found 72 of the 86 gold email spans, recall 0.837, below 0.95.
  Cause: 11 gold email spans include the square brackets around the
  address, 3 are placeholders (`[E-Mail]`, and two addresses whose domain
  is a bracketed placeholder). Neither is a pipeline fault; both are the gold
  noise the audit exists for. Fix: the boundary rule also trims opening
  brackets and quotes at the start and closing brackets and quotes at the
  end, for gold and predictions alike (`bench/c9/c9lib.py`, `norm`), since
  an address with and without brackets masks the same personal data. With it: 83 of 86,
  recall 0.965, the gate passes. The three placeholders stay as misses. The
  queue job `C9-regex` repeats the check and the other arms depend on it.
- Gold audit and run order: on Michael Boiman's direction of 2026-10-12 the
  arms run before the audit is done; publishing waits for it. Blindness is
  kept by the auditor not opening any C9 output (`results/c9/`, queue
  outputs) before the audit is finished. Form: `bench/c9/audit.py` builds
  `private/c9/gold-audit.html` (gitignored, the 40 documents with every
  gold span to judge and a field for missed spans); its export
  `private/c9/gold-audit.json` is what `bench/c9/score_c9.py` reads for the
  audited numbers and the gold precision and recall. The audit file is
  committed with the results (synthetic data, no personal data).
- Environments (prepared by `bench/c9/prep-pc.bat`, CPU only): Presidio
  2.2.364 with spaCy 3.8.16 and `de_core_news_lg` 3.8.0 in a venv of its own;
  the pattern recognisers of Presidio default to English, so the same
  classes (e-mail, IBAN, credit card, IP, phone with regions DE, AT, CH, US,
  GB) and the spaCy recogniser are registered for `de`; score threshold the
  library default. The two GLiNER (v1) arms use the `gliner` package 0.2.29,
  which needs transformers below 5.17, in front of the bench venv together
  with transformers 4.57.6 (`tf4`, as C1 and C6); their backbone tokenizer
  `microsoft/mdeberta-v3-base` at `a0484667b223`. `gliner2.5-multi` runs in
  the gliner2 2.0.0 venv of the ex1 arm.
- GLiNER arms: the 14 labels of `labels.json` (seven types, German and
  English), threshold 0.5, chunks of 384 words with 50 words overlap
  (`c9lib.chunks`; the longest document has 346 words, so chunking does not
  trigger on this set), duplicates across labels merged per span and type.
- LLM arms: the German instruction is in `bench/c9/run_c9.py`
  (`llm_prompt`) and in every `meta.json`; Ollama `format` schema with the
  seven types as enum, `think` off where the model has it, `num_ctx` 8192
  (the longest document has 2,640 characters), `num_predict` 2048. A
  returned text is located at every non-overlapping exact occurrence in the
  document; a text that is not found counts as a false positive (stored in
  `not_found` per row).
- Dry runs on the workstation (5 documents per arm, 3 for Gemma 4 12B, not
  scored, outputs not looked at beyond "runs and writes rows"): Presidio,
  the three GLiNER arms and Gemma 4 12B ran; Qwen3.8 27B shares the Gemma
  code path and model call and was not dry-run.
- Queue jobs `bench/queue/jobs/c9/`: regex (CPU, gate), Presidio (CPU), the
  three GLiNER arms, Gemma 4 12B and Qwen3.8 27B, the six depending on the
  regex job. Expected GPU time about 100 minutes, within the 1.5 h above.
