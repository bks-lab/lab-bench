# T12: local open model series on route1 and ex1

Test design, written 2026-10-09 and committed before any T12 run (the 20
item probes included). Roadmap row T12 of `plan/ROADMAP.md`. A change to
this design after the commit goes into a new dated section at the end,
never into the text above it.

## Question

What does one workstation with one RTX 4090 (24 GB) deliver on route1
(routing, all sources) and ex1 (slot extraction) with open-weight models,
by size class and maker? Which model is the best choice per task on such a
card, at what latency and throughput? Until now the local family had one
arm in route1 and ex1 (Winnow-12B), chosen on pv1. T12 measures the series
around it with the same harness, so that "the local LLM" in the tool map
is not one model's result.

Direction of Michael Boiman, 2026-10-09: focus on local open-weight
models and what this workstation can do. T5 (hosted LLM) is dropped.

### Excluded, with the reason

- `qwen3:4b`, `qwen3:30b-a3b` (thinking-2507 builds): thinking-only,
  see above.
- `deepseek-r1:32b`: a pure reasoning model, it thinks before every answer
  and has no switch to answer with a bare letter. Not scored.
- `nemotron-3-nano:30b`: NVIDIA Open Model Licence (use restrictions), and
  its 24.3 GB Q4 build does not fit the card next to the desktop's use.
- `gpt-oss:20b`: reasoning model (harmony format, reasoning effort can be
  lowered but not switched off).
- Llama 3.x 8B: Llama community licence, not an open licence by the rule
  above.
- `gemma4:31b`, `gemma4:26b-a4b`: left out for run time; the Gemma 4
  family is covered by e4b, 12b, Winnow-12B and shisa-de-1 (on 26B-A4B).

## Method, identical to Winnow-12B in route1 and ex1

Same runners, same prompts, same parameters as the Winnow-12B rows of
2026-10-09:

- route1: `bench/run-local.mjs --pv route1 --runs 1 --skip-over-26
  --prefix ''`, system line "You classify a short text. Answer each
  multiple-choice question with the letter of exactly one option.",
  options as letters, temperature 0, one token, top 20 logprobs,
  `num_ctx` 16384. The 100 `support_intent:intent` questions (28 options)
  are unanswered rows, as for Winnow-12B.
- ex1: `bench/run-local-extract.mjs`, the same slot prompt, Ollama
  `format: "json"`, temperature 0, `num_predict` 512, `num_ctx` 4096, the
  same 1,000 + 1,000 utterances.
- Ollama 0.35.0 on the workstation, called from the Mac over the LAN,
  `HOST_LABEL=local-rtx4090:11434`.

### Template rule

Every call is a raw prompt in the model's own chat template: the turn
markers of the template that Ollama ships with the model (`/api/show`,
field `template`, or the built-in renderer it names) for one system turn,
one user turn and the opening of the assistant turn, nothing else. Where
the model has a thinking mode, thinking is switched off by the mechanism
of its own template:

| template | models | system, user, assistant opening | thinking off |
|---|---|---|---|
| `chatml` | Qwen3, Qwen3.8 | `<\|im_start\|>system ... <\|im_end\|>` etc. | empty `<think>\n\n</think>\n\n` block (Qwen3's documented non-thinking form) |
| `gemma4` | Gemma 4, Winnow-12B, shisa-de-1 | `<\|turn>system ... <turn\|>` etc. | empty thought channel `<\|channel>thought\n<channel\|>` |
| `phi4` | Phi-4 | `<\|im_start\|>system<\|im_sep\|> ... <\|im_end\|>` | no thinking mode |
| `mistral` | Mistral Small 3.2 | `[SYSTEM_PROMPT] ... [/SYSTEM_PROMPT][INST] ... [/INST]` | no thinking mode |
| `granite` | Granite 4 | `<\|start_of_role\|>system<\|end_of_role\|> ... <\|end_of_text\|>` | no thinking mode (Granite 4 instruct has none) |

`phi4`, `mistral` and `granite` are new in both runners; each is copied
from the model's Ollama template before its probe, and the template text is
saved next to the probe (`results/t12/templates/<arm>.txt`). Check: the
probe also sends the same system and user message through `/api/chat`
(Ollama renders its own template) and records both prompt token counts; the
raw prompt may differ only by the thinking-off block (up to 5 tokens)
and whitespace. The driver stops a model whose two counts differ by more
than 6 tokens, until the template is fixed (and the fix is recorded).
Known difference, kept on purpose: Ollama's Qwen3 template puts an extra
blank line after `<|im_start|>system`; the `chatml` template of the runner
follows the Hugging Face Qwen3 template without it, as in the pv1 and
einv1 Qwen arms, so it stays unchanged.

### Letter-mass probe, before every full run

Per model, before its full route1 run: `run-local.mjs --pv route1
--per-group 4 --tag probe`, which is 20 questions (4 MASSIVE de requests,
4 MASSIVE en requests, two questions each, and 4 fast-decisions rows with
4 questions in total). Recorded as `results/route1/<arm>/<date>-run1-probe.jsonl`
and in `results/t12/probes.md`.

- Median letter mass over the 20 >= 0.5: the full run uses prefix `''`,
  as Winnow-12B.
- Below 0.5: the probe is repeated once with the pv1 prefix
  `'Answer: **'` (the documented fix for Qwen's bold letters,
  `bench/run-local.mjs`). If that probe reaches 0.5, the full run uses it
  and the findings say so per model.
- Still below 0.5: the model is reported as **format failure** for
  route1 and gets no accuracy in the series table. Its ex1 run still
  happens (JSON mode does not depend on the letter).
- The full run is also checked afterwards: a model whose median letter
  mass over its full route1 run is below 0.5 is reported as format
  failure there, with its accuracy shown only in parentheses.

Probe answers are not looked at for accuracy and change nothing but the
prefix choice above.

## Machine measurements per model

Driver: `bench/run-t12.mjs` (committed with this design) runs the steps
below for one model after the other and calls the two runners; the raw
prompts of all templates come from `bench/lib/templates.mjs`, shared by the
runners and the driver's template check.

One model on the GPU at a time. Before each model: every model unloaded
(`keep_alive: 0`), idle VRAM read with `nvidia-smi`. Then:

- **load time**: one `/api/generate` with an empty prompt after the unload,
  Ollama's `load_duration`.
- **VRAM**: `nvidia-smi --query-gpu=memory.used` sampled during the full
  run, maximum minus the idle value; plus `size` and `size_vram` from
  `/api/ps` (a `size_vram` below `size` means layers on the CPU, reported).
- **latency**: median `latency_ms` per decision (route1) and per utterance
  (ex1), from the rows; `compute_ms` beside it.
- **decisions per hour**: route1 rows / wall time of the run (first to
  last row timestamp) x 3600; ex1 utterances per hour the same way. One
  stream, no batching, no parallel requests.

Stored in `results/t12/machine.json` and the findings.

Runs are strictly sequential, one model after the other. The workstation
also hosts GitHub runners and the desktop; a job of theirs during a run
can slow it, and the findings note any visible effect. Nothing on the
machine is stopped for the test.

## Scoring

- `bench/score-route.mjs` and `bench/score-extract.mjs` score every arm,
  so the new arms appear in `results/route1/score.md` and
  `results/ex1/score.md` beside the existing ones. Existing rows of those
  reports keep their numbers.
- Per model, in `results/t12-findings.md`: route1 accuracy for MASSIVE
  scenario (de, en), MASSIVE intent 2+ options (de, en), fast-decisions
  with 26 labels or fewer (en); ex1 slot F1 and exact frame (de, en);
  median letter mass; latency; VRAM; decisions per hour.
- A size vs accuracy reading over the classes, descriptive.
- "Best choice per task on a 24 GB card" is read off the same test data,
  so it is chosen after the fact and labelled so.

## The tool map: one pre-named local arm per size class

Picking the best of twelve local models after the fact would flatter the
local family. So:

- The `local-llm` family cell of every existing row stays what it is: its
  eligible arm in route1 and ex1 remains `winnow-12b` (the arm named in
  `results/route1/method.md` before those runs), in pv1 the four arms of
  `results/pv1/method.md`. Existing cells do not change.
- route1 and ex1 rows get a new field `local_size_classes` with one
  column per class, each filled by **one representative named here,
  before any run**:

  | column | representative |
  |---|---|
  | `small` | `qwen3-4b` |
  | `medium` | `qwen3-14b` |
  | `large` | `qwen3-32b` |
  | `moe` | `qwen3-30b-a3b` |

  Rule behind the choice: one generation of one maker (Qwen3, all four
  released together, same training recipe) in every class, so the columns
  show size and architecture, not maker. Each column carries value,
  baseline, skill, n, answered, median latency and, for route1, the McNemar
  p against Jev, as in the report. A representative with a format failure
  keeps its column with `format_failure: true` and no value.
- Every other local model appears only in the series table of
  `results/t12-findings.md`, never in the map.
- The automation rows (T1) keep their local arms (`winnow-12b` in route1,
  the four pv1 arms); T12 does not compute automation rates.

The diff of `results/toolmap.json` is therefore additions only (the
`local_size_classes` fields, a note, the generation date); any other
change is a bug.

## Thresholds and tests fixed in advance

- One contrast per route1 row is tested: `qwen3-32b` against `qwen3-4b`
  (large against small, same family), exact two-sided McNemar on the paired
  items, p < 0.05, no correction (five rows). Every other comparison
  between local models is descriptive.
- McNemar against Jev is printed for every arm by the scorer, as before;
  for the eleven new arms it is descriptive.
- A model counts as usable for a route1 task at a skill of 0.5 or more on
  that row, as everywhere in the map.
- Format failure: median letter mass below 0.5, as above.

## Order

Representatives first, so the map columns exist even if the series is
cut short: `qwen3-4b`, `qwen3-14b`, `qwen3-30b-a3b`, `qwen3-32b`, then
`gemma4-e4b`, `granite4-micro`, `phi4-14b`, `gemma4-12b`,
`mistral-small3.2-24b`, `qwen3.8-27b`, `shisa-de-1`. Per model: probe,
route1, ex1, unload.
